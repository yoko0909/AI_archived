## Codex

已查明：原因不是 Excel 或导表顺序，而是第 198 行使用了 `pairs` 遍历字典表。

- Excel `层数表|RaidFloor` 按 `FloorId` 升序排列。
- 当前客户端导表 [RaidFloor.lua](/F:/Pan1/demo/EM/Content/Script/Datas/RaidFloor.lua:9) 也按 `1001...1181、2001...2181` 顺序生成，键集合和 Excel 一致。
- 但 `RaidFloor` 的结构是：

```lua
{
    [1001] = {...},
    [1002] = {...},
}
```

这是数字键字典，不是连续数组。

- 第 198 行：

```lua
for _, v in pairs(DataMgr.RaidFloor) do
```

`pairs` 底层使用 Lua 的 `next`，遍历的是哈希表桶顺序，不保证按照 Lua 源码、Excel 行号或数字键升序。Lua 5.4 源码中 `luaH_next` 会按数组区和哈希区遍历，而不是按键值排序。
- `DataMgr.ReadOnly` 的 `__pairs` 只是继续调用底层表的 `pairs`，没有做排序，见 [DataMgr.lua](/F:/Pan1/demo/EM/Content/Script/DataMgr.lua:319)。
- 随后结果被 `table.insert` 到 `resultList`，并在 [LevelSelect.lua](/F:/Pan1/demo/EM/Content/Script/BluePrints/UI/WBP/Play/Widget/GuildWar/WBP_Activity_GuildWar_LevelSelect_C.lua:331) 中按 `ipairs` 创建 UI，因此哈希遍历顺序最终变成了界面顺序。

因此截图里的顺序是 Lua 调试器/运行时的哈希遍历顺序，不代表 Excel 顺序。若要求固定顺序，需要在构造 `resultList` 后按 `Floor` 或 `FloorId` 显式 `table.sort`，或者按连续 ID 逐项索引。

另外，`ExportDatas/output` 下的 `RaidFloor.lua` 是 8 月 31 日的旧导出，仅有 20 条；当前运行时实际使用的 `Content/Script/Datas/RaidFloor.lua` 是 9 月 7 日版本，共 362 条。
