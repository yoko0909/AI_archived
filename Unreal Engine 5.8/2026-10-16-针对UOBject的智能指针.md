# 对话记录

## 用户

针对UOBject的智能指针

## Codex

针对 UObject，不要用 std::shared_ptr、TSharedPtr 或 TUniquePtr 管理生命周期，因为 UObject 由 Unreal GC 管理。

常用类型如下：

| 类型 | 用途 |
|---|---|
| TObjectPtr<T> | UE5 中推荐的强引用成员指针，会被 GC 识别 |
| TWeakObjectPtr<T> | 弱引用，不阻止对象被 GC |
| TSoftObjectPtr<T> | 软引用，保存资源路径，可延迟加载 |
| TSubclassOf<T> | 保存某个 UObject 子类的类引用 |
| TStrongObjectPtr<T> | 临时创建 GC 强引用，使用场景较少 |

`cpp
UCLASS()
class UMyComponent : public UActorComponent
{
    GENERATED_BODY()

public:
    UPROPERTY()
    TObjectPtr<UObject> Target;

    TWeakObjectPtr<AActor> CachedActor;

    UPROPERTY(EditAnywhere)
    TSoftObjectPtr<UTexture2D> Icon;
};
`

TObjectPtr 是 GC 可追踪的对象引用，但不是传统意义上的引用计数智能指针。长期保存的 UObject 强引用成员通常使用 UPROPERTY() TObjectPtr<T>。

## Codex

两个目录都确认是完整的 Unreal 源码树。UE4.27 工作区没有 ObjectPtr.h、TObjectPtr、CPF_TObjectPtr 或 FObjectPtr；UE5.8 增加了这些对象句柄和对象指针基础设施。

UE4.27 中常见的强引用形式是：

`cpp
UPROPERTY()
UMyObject* Object;
`

UE5.8 中推荐改为：

`cpp
UPROPERTY()
TObjectPtr<UMyObject> Object;
`

两者在最核心的 GC 语义上都是强引用。UE5.8 的变化主要是把对象引用包装成引擎能够识别、分类和进一步追踪的专用类型。

两版都存在 TWeakObjectPtr<T>、TSoftObjectPtr<T> 和 TStrongObjectPtr<T>。UE5.8 的软引用加载接口和 TStrongObjectPtr 内部实现更丰富，但基本用途保持一致。

UE4.27 的核心模型是：

`	ext
UPROPERTY + UObject* 负责常规强引用
TWeakObjectPtr        负责弱引用
TSoftObjectPtr        负责路径和延迟加载
TStrongObjectPtr      负责非 UPROPERTY 场景下显式保活
`

UE5.8 的核心模型是：

`	ext
UPROPERTY + TObjectPtr 负责常规强引用
TWeakObjectPtr         负责弱引用
TSoftObjectPtr         负责路径和延迟加载
TStrongObjectPtr       负责非 UPROPERTY 场景下显式保活
FObjectPtr/ObjectHandle 提供底层句柄与追踪基础设施
`

## 用户

对于UObject的智能指针和UPERPROTY可以共同使用么？优劣是什么？

## Codex

可以共同使用，而且在 UE5 中这是推荐写法：

`cpp
UPROPERTY()
TObjectPtr<UMyObject> Object;
`

这里两者职责不同：TObjectPtr 是指针类型，UPROPERTY 是让 Unreal 反射系统和 GC 能识别该成员的声明宏。

- TObjectPtr 保存对 UObject 的引用。
- UPROPERTY 让引擎追踪、序列化、编辑器显示、蓝图访问或网络复制。
- 对象生命周期仍由 Unreal GC 管理，不是引用计数。

没有 UPROPERTY 的 TObjectPtr 通常不会自动参与反射、序列化和常规 GC 引用扫描，需要额外通过 FGCObject、AddReferencedObjects 或 TStrongObjectPtr 处理。

UPROPERTY() UMyObject* Object; 在 UE4.27 中是主要写法，在 UE5 中仍兼容。UE5 新代码通常推荐 UPROPERTY() TObjectPtr<UMyObject> Object;。

TWeakObjectPtr 即使加了 UPROPERTY 也不会变成强引用；TSoftObjectPtr 保存的是路径而不是直接保持对象实例存活；TStrongObjectPtr 主要用于普通 C++ 所有者。

## 用户

TObjectPtr  的原理是什么？存在的价值是什么？

## Codex

TObjectPtr 是 FObjectPtr 的类型化包装，底层通过 FObjectHandle 或等价的对象句柄保存引用。根据编译配置，句柄可以表示已经解析的对象地址、尚未解析的对象引用、延迟解析句柄或远程对象引用。

UE5.8 源码注释说明，TObjectPtr 的目标是作为 UObject 裸指针成员的替代品，支持对象句柄、访问追踪和可选的编辑器延迟加载行为；解析后，它参与 GC 的方式与 UObject 裸指针相同。

真正让它成为 GC 强引用的关键仍然是：

`cpp
UPROPERTY()
TObjectPtr<UMyObject> Object;
`

UE5 的反射系统将这种成员识别为 FObjectProperty，并通过 GC schema 记录对象引用。TObjectPtr 本身不是 GC Root，也不是引用计数指针。

它的主要价值包括：

- 支持对象句柄和延迟解析。
- 支持编辑器 Lazy Load、访问追踪和 Cook 依赖分析。
- 为未来的压缩引用、对象表索引和远程对象引用保留扩展空间。
- 在增量可达性分析期间提供赋值写屏障。
- 统一 C++ 对象成员、反射、序列化和 GC 的对象引用表达。

它不负责自动析构、引用计数、跨线程安全或替代 TSharedPtr/TUniquePtr。

## 用户

对于UE的GC而言，TObjectPtr使用和不适用的区别有什么异同？

## Codex

需要把“指针类型”和“GC 是否能发现它”分开看。

`cpp
UPROPERTY()
TObjectPtr<UMyObject> ObjectA;

UPROPERTY()
UMyObject* ObjectB;
`

这两个成员都会被反射系统注册为对象属性，并参与 GC 引用扫描。UE5.8 中，FObjectProperty::EmitReferenceInfo 会把对象属性加入 GC 引用 schema，因此在普通完整 GC 中，两者都能形成 GC 强引用。

但下面这种写法不能仅凭 TObjectPtr 保证对象存活：

`cpp
TObjectPtr<UMyObject> Object;
`

没有 UPROPERTY 时，通常不会自动进入 UObject 的反射属性扫描；需要手动通过 FGCObject 或其他 GC 机制注册。

增量可达性分析是两者最重要的差异：TObjectPtr 赋值时可以在 GC pending 状态下调用 MarkAsReachable，而普通 UObject* 赋值无法自动触发该写屏障。

`	ext
完整 GC：
两者被扫描后，行为基本相同

增量 GC：
TObjectPtr 能在赋值时通知 GC
UObject* 普通赋值无法自动通知 GC
`

UE4.27 中没有 TObjectPtr 和对象句柄体系；传统模型是 UPROPERTY + UObject*。

## 用户

对于在增量GC中的关键差异，请你举个具体的示例说明。

## Codex

假设有两个持有者：

`cpp
UCLASS()
class UHolder : public UObject
{
    GENERATED_BODY()

public:
    UPROPERTY()
    TObjectPtr<UObject> SafeObject;

    UPROPERTY()
    UObject* RawObject = nullptr;
};
`

GC 第一个时间片先扫描 Holder，此时两个成员都是空。之后增量 GC 暂停，游戏逻辑创建对象并执行：

`cpp
UObject* ObjectA = NewObject<UObject>();
UObject* ObjectB = NewObject<UObject>();

Holder->SafeObject = ObjectA;
Holder->RawObject = ObjectB;
`

TObjectPtr 的赋值会检查 GIsIncrementalReachabilityPending，并在条件满足时调用 UE::GC::MarkAsReachable(ObjectA)。普通裸指针赋值无法被 C++ 拦截，也不会自动通知 GC。

如果 ObjectA 和 ObjectB 都没有其他强引用，ObjectA 可以通过写屏障重新进入可达对象处理流程，而 ObjectB 可能在本轮增量 GC 中漏标并进入回收流程。

此例的成立条件是：持有者已经被扫描、增量可达性分析仍未完成、对象没有其他强引用。若引用在持有者扫描之前建立、对象还有其他强引用，或只是增量销毁而非增量可达性分析，则通常没有这个特定问题。

## Codex

结论：

1. TObjectPtr 相比 UObject* 的自动写屏障，主要解决的是增量可达性分析跨帧进行时的引用变化问题。
2. UE4.27.2 已经有“增量 GC”，但主要是增量销毁/清理，不是增量标记。
3. UE5.8 增加了跨帧的增量可达性分析，但源码中默认关闭，需要 gc.AllowIncrementalReachability=1。
4. UE4.27 中，标记阶段完成后再建立引用，不能挽救已经被判定为不可达的对象。

UE4.27 的增量机制位于 BeginDestroy/FinishDestroy/Unhash 的清理阶段，而可达性标记在一次 CollectGarbageInternal 中同步完成。UE5.8 则额外支持跨帧挂起的增量可达性分析。

在同步可达性分析中，GC 会同步完成标记对象不可达、扫描根对象、递归扫描引用、确定可达对象和确定不可达对象。GC 标记阶段不会在“扫描 Holder”和“继续扫描”之间返回游戏逻辑。

UE4.27 的流程可以概括为：

`	ext
同步可达性分析
    ↓
GatherUnreachableObjects
    ↓
得到不可达对象列表
    ↓
后续 Tick 分批 BeginDestroy / Purge
`

正常游戏线程流程下，GC 标记期间不会出现游戏逻辑突然建立引用的情况。GC 锁和 FGCScopeLock 用来协调 UObject 操作；GC 内部可以并行扫描，但外部游戏逻辑不会同时修改引用关系。

如果对象已经被判定为 Unreachable，之后再给某个 UObject 建立引用，也不能可靠地把它复活。TObjectPtr 不是引用计数指针，也不能复活已经进入 BeginDestroy 或 PendingKill 生命周期的对象。

## Codex

是的，上一条概括不准确：

`	ext
TObjectPtr 写屏障主要服务于增量可达性标记，不是增量销毁。
`

UE5.8 中，TObjectPtr 赋值时会检查 GIsIncrementalReachabilityPending，如果增量可达性分析尚未完成，就调用 UE::GC::MarkAsReachable(Obj)。

准确总结：

`	ext
UE4.27：同步可达性标记 + 增量销毁
UE5.8 默认：同步可达性标记 + 增量销毁
UE5.8 开启增量可达性后：增量可达性标记 + 增量销毁
`

UE4.27 主要依靠同步执行和 GC 锁，而不是 TObjectPtr 写屏障。CollectGarbage() 会先获取 GC 锁，再同步调用 CollectGarbageInternal()，完成 PerformReachabilityAnalysis 和 GatherUnreachableObjects。

因此不是单线程 GC，而是：

`	ext
游戏逻辑线程被同步阻塞；
GC 内部可以并行扫描；
外部 UObject 操作通过 GC Lock 互斥。
`

增量销毁发生在可达性分析之后。一旦对象进入不可达对象列表，后续在增量清理期间建立引用不能使它重新成为本次 GC 的存活对象。

在UE5中对于TObjectPtr的引入，我理解上主要是为了UE5的增量GC的新特性服务的，对么？那如果我开启了增量GC，但是对于U类中的成员，只添加了UPERPROTy没有加TObjectPtr是不是就可能会出现问题，导致这个成员被回收销毁掉。

## Codex

需要把“开启增量 GC”具体限定为开启增量可达性分析：

`ini
gc.AllowIncrementalReachability=1
`

UE5.8 中该选项默认关闭：

`cpp
static int32 GAllowIncrementalReachability = 0;
`

TObjectPtr 不只是为了增量 GC，它还服务于对象句柄、延迟解析、编辑器 Lazy Load、Cook 依赖追踪、访问追踪和未来对象引用表示形式的演进。但在增量可达性分析期间自动建立写屏障，确实是它的重要价值之一。

例如：

`cpp
UPROPERTY()
UObject* Target;
`

它仍然是 GC 可识别的强引用，UPROPERTY 决定 GC 扫描该成员，所以不能说它一定会失效。但是如果同时满足以下条件，就存在被错误回收的可能：

1. 开启 gc.AllowIncrementalReachability=1。
2. GIsIncrementalReachabilityPending == true。
3. Target 的持有者已经被 GC 扫描过。
4. 此时才执行 Holder->Target = TargetObject。
5. TargetObject 没有其他 GC 强引用。

这时普通裸指针赋值不会自动通知 GC；使用 UPROPERTY() TObjectPtr<UObject> Target 时，赋值会通过 FObjectPtr::operator= 检查增量 GC 状态，并在需要时调用 UE::GC::MarkAsReachable。

以下情况通常没有这个特定风险：引用在 GC 开始前建立、Holder 尚未被扫描、Target 还有其他强引用、只启用了增量销毁，或者执行的是同步可达性分析。

实际建议是 UE5 中长期保存的强引用成员使用：

`cpp
UPROPERTY()
TObjectPtr<UMyObject> Target;
`

UPROPERTY 让 GC 知道这是对象引用，TObjectPtr 让引用赋值具备对象句柄、访问追踪和增量 GC 写屏障能力。TObjectPtr 不是引用计数指针，也不能复活已经进入 BeginDestroy、PendingKill 或其他销毁阶段的对象。
